# Webhooks (Milestone 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An organizer registers a webhook URL and receives HMAC-signed `booking.confirmed` and `booking.expired` notifications, retried with exponential backoff, dead-lettered when they keep failing, with a delivery log readable through the API.

**Architecture:** A booking outcome writes a `webhook_deliveries` row in the same transaction that confirms or expires the hold, so a notification exists if and only if the outcome commits. The worker's dispatcher claims due rows (short transaction, lease), posts them over HTTP outside any transaction, and records each attempt in `webhook_attempts`. A failed attempt schedules the next one with exponential backoff; after the last attempt the delivery becomes `DEAD`, which the organizer can list and retry.

**Tech Stack:** As milestone 2. Spring `RestClient` over the JDK `HttpClient`; `javax.crypto.Mac` for HMAC-SHA256; the JDK's `com.sun.net.httpserver.HttpServer` as the test receiver. No new dependencies.

**Spec:** `DESIGN.md` (repo root), milestone 3: flow step 5 (Notify) and the test "A webhook receiver that fails N times: retried with backoff, then dead-lettered."

## Decisions made in this plan (plan author's calls, not agreed in detail)

- **The database is the webhook queue, not Kafka.** Both outcomes (confirm, expire) already happen in the worker, so a Kafka hop would carry messages from the worker to itself. Retries need a "not before" time per message, which a table gives and a Kafka partition does not (a retrying record blocks its partition, as milestone 2 showed). This also sidesteps milestone 2's outbox per-key ordering limit, because webhooks do not use the outbox.
- **The dead-letter table is the `DEAD` status of `webhook_deliveries`**, not a second table. A separate table would copy the row and its attempt history for no gain; `GET /webhook-deliveries?status=DEAD` is the dead-letter view, and `POST /webhook-deliveries/{id}/retry` replays one. This departs from DESIGN.md's wording "dead-letter table"; the README says so.
- **Events get an organizer.** `POST /events` now requires the `X-User-Id` header, stored as `events.organizer_id`. Each organizer has at most one webhook endpoint (`PUT /webhook-endpoint`).
- **No `hold_seats` table.** `booking.expired` needs the seat ids, which the sweep clears; the sweep's CTE reads them from its own pre-update snapshot instead.
- **Only the two events the spec names.** A declined payment releases seats without a webhook.
- **At-least-once, unordered.** A crash between a successful POST and recording it causes a repeat; receivers dedupe on `Seatlock-Delivery-Id`. Deliveries are not ordered relative to each other.
- **Signature format** (Stripe-like, so receivers recognise it): header `Seatlock-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(secret, "<t>.<raw body>")>`. Signed fresh on every attempt.
- **Secrets are stored in plain text**, because signing needs them. Documented as a shortcut.
- **SSRF guard.** URLs must be `https` and resolve to public addresses; two properties relax this for local runs and tests. This matters before milestone 4's public deploy.

## Global Constraints

- Everything in milestone 1's and 2's Global Constraints still holds (Java 21, Spring Boot 4.1.x, `JdbcClient` not JPA, injected `Clock`, `ProblemDetail` errors, UUID ids, Testcontainers not mocks, `X-User-Id` header, `@DirtiesContext(AFTER_CLASS)` on any test that turns a background component on, no retrying deadlocks or unique violations to hide a race, versions from the Boot BOM).
- Event types are exactly `booking.confirmed` and `booking.expired`.
- Request headers sent to receivers: `Content-Type: application/json`, `Seatlock-Delivery-Id: <delivery uuid>`, `Seatlock-Event-Type: <type>`, `Seatlock-Signature: t=<unix seconds>,v1=<64 lowercase hex chars>`.
- Payload: `{"id":"<delivery uuid>","type":"<type>","createdAt":"<ISO-8601 instant>","data":{...}}`. `data` for `booking.confirmed`: `holdId, eventId, userId, seatIds, paymentId, amountCents, currency`. For `booking.expired`: `holdId, eventId, userId, seatIds`. `seatIds` sorted by seat label as numbers.
- Secret format: `whsec_` followed by 32 random bytes from `SecureRandom`, base64url without padding. The HMAC key is the UTF-8 bytes of the whole string.
- Success is any 2xx. Redirects are not followed (a 3xx is a failure). Connect timeout 2 s, read timeout 5 s. At most 1,000 characters of response body are kept per attempt.
- Retry: `seatlock.webhooks.max-attempts: 6`; after failed attempt `n` (1-based) the next attempt is due at `now + base-backoff × 2^(n-1)` with `seatlock.webhooks.base-backoff: PT10S` (10 s, 20 s, 40 s, 80 s, 160 s). Failed attempt 6 makes the delivery `DEAD`.
- New switch, default on: `seatlock.webhooks.enabled` (the dispatch job). `application-api.yaml` turns it off; `@IntegrationTest` turns it off by default.
- URL policy properties, default false: `seatlock.webhooks.allow-http`, `seatlock.webhooks.allow-private-addresses`. `@IntegrationTest` sets both true.

## Review Focus

1. An organizer registers a URL pointing at `localhost`, `169.254.169.254` or a `10.x` address on a deployed instance: 400 at registration, and an attempt to a URL that later resolves to such an address fails without a request being sent. → Tasks 2 and 4.
2. The receiver hangs longer than the read timeout: the attempt is recorded as a failure with the error, and the dispatcher moves on. → Task 4.
3. Two dispatchers (two worker replicas) run at once: every delivery is posted exactly once. → Task 4.
4. A payment is settled twice (duplicate Kafka message) or expiry sweeps run concurrently: exactly one delivery per outcome. → Task 3.
5. An organizer asks for another organizer's delivery: 404, as if it did not exist. → Task 5.

### Task 4: Signing and dispatch with retries

**Files:**
- Create: `webhook/WebhookSigner.java`, `webhook/WebhookDispatcher.java`, `webhook/WebhookDispatchJob.java`, `webhook/WebhookHttpConfig.java`
- Modify: `webhook/WebhookDeliveryRepository.java`, `test/.../ProfileWiringTest.java`
- Test: `webhook/TestReceiver.java`, `webhook/WebhookSignerTest.java`, `webhook/WebhookDispatcherTest.java`

**Interfaces:**
- Produces: `WebhookSigner.signatureHeader(String secret, long unixSeconds, String body)` → `"t=<s>,v1=<hex>"`.
- Produces: `WebhookDispatcher.dispatchBatch()` → number of deliveries attempted. Algorithm:
  1. **Claim** (own short transaction, package-private `claim()`): `update webhook_deliveries set attempts = attempts + 1, next_attempt_at = now + lease where id in (select id ... where status = 'PENDING' and next_attempt_at <= now order by next_attempt_at, id limit batch-size for update skip locked) returning ...`, joined to the endpoint's current `url` and `secret`.
  2. **Send** each claimed row outside any transaction: check `WebhookUrlPolicy` first (a violation is a failed attempt with that error, no request sent), then POST with the headers from Global Constraints, signed with `clock.instant()`.
  3. **Record** each result (own short transaction): insert a `webhook_attempts` row numbered `coalesce(max(attempt), 0) + 1` for that delivery (not the claimed count: Task 5's retry resets the count but keeps old attempt rows); on 2xx set `DELIVERED` and `delivered_at`; on failure set `next_attempt_at = now + base-backoff × 2^(attempts-1)`, or `DEAD` when `attempts >= max-attempts`. Guard the update with `where id = ? and attempts = ? and status = 'PENDING'` (the claimed value), and skip the attempt insert when it matches nothing, so a stale sender cannot overwrite a newer claim.
  - The lease means a crashed or stalled sender's row becomes due again after `lease`; that is the at-least-once path.
- Produces: `WebhookDispatchJob` (`@ConditionalOnProperty seatlock.webhooks.enabled`, `matchIfMissing = true`; `@Scheduled(fixedDelayString = "${seatlock.webhooks.interval:PT1S}")`). `WebhookHttpConfig` builds the `RestClient` on a JDK `HttpClient` with `Redirect.NEVER`, connect timeout 2 s, and a 5 s read timeout on the request factory; any status is handed to the dispatcher rather than thrown.
- Test helper `TestReceiver`: wraps a JDK `HttpServer` on port 0; queue of scripted responses (status, optional body, optional delay), default 200; records each request's headers and body; `url()` returns `http://localhost:<port>/hook`; `AutoCloseable`.
