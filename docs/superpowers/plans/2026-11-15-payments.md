# Payments (Milestone 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A buyer pays for a hold; the payment is settled asynchronously through Kafka, recorded in a double-entry ledger, and can never be charged or confirmed twice.

**Architecture:** The pay request records a PENDING payment and an outbox row in one transaction and returns. A relay publishes outbox rows to Kafka. A consumer settles each payment against a fake provider, writes balanced ledger entries and confirms or releases the hold. One codebase runs as two deployables selected by Spring profile: `api` (web + outbox relay) and `worker` (Kafka consumer + hold expiry, no web server).

**Tech Stack:** As milestone 1, plus Spring for Apache Kafka, Testcontainers Kafka, Awaitility.

**Spec:** `DESIGN.md` (repo root), milestone 2: flow steps 2 (Pay) and 3 (Settle).

## Decisions made in this plan (plan author's calls, not agreed in detail)

- **One codebase, two profiles**, instead of two Maven modules. Both roles share the schema, the SQL and the test infrastructure, and an end-to-end test can run both in one process. The cost is that the two deployables ship the same jar. `booking-api/` is renamed `app/` because it no longer only serves the API.
- **A paying hold cannot expire.** Paying moves the hold to `PAYMENT_PENDING`, which the expiry sweep ignores.
- **No bookings table.** A `CONFIRMED` hold with `BOOKED` seats is the booking.
- **Events get a price.** `priceCents` and `currency` become required when creating an event.
- **No refunds in this milestone.** The ledger shape allows reversal entries later.
- **The fake provider is driven by the amount**, like test card numbers: an amount ending in `01` cents is declined, ending in `02` times out, anything else is approved.

## Global Constraints

- Everything in milestone 1's Global Constraints still holds (Java 21, Spring Boot 4.1.x, `JdbcClient` not JPA, injected `Clock`, `ProblemDetail` errors, UUID ids, Testcontainers not mocks, `X-User-Id` header).
- Money is integer minor units in a `long` named `...Cents`, with a 3-letter `currency`. Never floating point.
- Kafka topic `payments.requested`; consumer group `seatlock-worker`; message key is the payment id; message value is the JSON `{"paymentId":"<uuid>"}`.
- `Idempotency-Key` is a required request header on pay, at most 255 characters.
- Scheduled and listening components are switched by properties, default on: `seatlock.expiry.enabled`, `seatlock.outbox.enabled`, `seatlock.settlement.enabled`. `@IntegrationTest` turns all three off; tests that need one turn it on explicitly.
- Never retry a database deadlock or unique violation to hide a race; the statements below are ordered to avoid them. Translating a unique violation into the right client error is allowed where a task says so.
- A test class that turns a background component on (relay, listener, expiry job) must close its Spring context afterwards (`@DirtiesContext(classMode = AFTER_CLASS)`), so a cached context cannot publish, settle or expire rows belonging to later tests.
- Dependency versions come from the Spring Boot BOM; find starter names on start.spring.io for the Boot version in use, do not guess them.

## Review Focus

1. The same `Idempotency-Key` reused for a different hold: 422, nothing changed. → Task 3.
2. Paying a hold whose time has run out but which the sweep has not reached yet: 409, hold stays ACTIVE and is swept normally afterwards. → Task 3.
3. Paying someone else's hold: 404, nothing changed. → Task 3.
4. The provider approved a charge but the worker died before committing: on redelivery the buyer is charged once. → Task 5.
5. A Kafka message that is garbage or names a payment that does not exist: skipped, and the consumer keeps processing later messages. → Task 6.

- [ ] **Step 4: Implement `requestPayment` with this algorithm, in one `@Transactional` method**

```sql
-- 1. claim the hold; the row lock serialises concurrent pay requests for it
update holds set status = 'PAYMENT_PENDING'
 where id = :holdId and user_id = :userId and status = 'ACTIVE' and expires_at > :now
returning event_id;

-- 2. no row claimed → look for an earlier payment with this key
select ... from payments where user_id = :userId and idempotency_key = :key;
--    found, same hold      → return it (this is a replay)
--    found, different hold → IdempotencyKeyConflictException
--    not found             → NotFoundException if no hold with this id and user exists,
--                            otherwise HoldNotPayableException

-- 3. row claimed, but the key already belongs to another hold's payment
--    → IdempotencyKeyConflictException (the transaction rolls the claim back)

-- 4. amount = (seats with hold_id = :holdId) × events.price_cents
-- 5. insert into payments (... status 'PENDING')
--    a unique violation on (user_id, idempotency_key) here means two different holds raced
--    with one key: translate it to IdempotencyKeyConflictException
-- 6. OutboxRepository.add("payments.requested", paymentId, {"paymentId":"<id>"}, now)
```

The claim comes first so that a simultaneous second request waits on the hold row and then finds the first one's payment in step 2.
