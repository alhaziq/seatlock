# Proof (Milestone 4) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the headline provable and public: real login, Redis for rate limiting and cached seat reads, metrics with a dashboard, a k6 load test whose results are checked in SQL, and everything packaged to run on one VM with Docker Compose.

**Architecture:** `X-User-Id` is replaced by a signed JWT (HS256) issued at login; the user id is the token's `sub`. Redis holds per-user rate-limit counters and a short-lived copy of each event's seat list; it is never asked who holds a seat, and if it is down the app fails open. Micrometer exports to Prometheus on an internal management port; Grafana shows a provisioned dashboard. One `compose.prod.yaml` runs Postgres, Kafka, Redis, the api, the worker, Prometheus, Grafana and Caddy (TLS) on a single VM.

**Tech Stack:** As milestone 3, plus Spring Security OAuth2 resource server (Nimbus JWT), Spring Data Redis (Lettuce), Micrometer Prometheus registry, Testcontainers Redis, k6, Prometheus, Grafana, Caddy.

**Spec:** `DESIGN.md` (repo root): milestone 4 "Proof", the Goals, the headline, "Shared infrastructure: Redis", Stack, and the open item "Where it is hosted and what it may cost".

## Decisions made in this plan (plan author's calls, not agreed in detail)

- **Login is username + password, stored with BCrypt.** `POST /auth/signup` and `POST /auth/login`; no email, reset, roles or refresh tokens (DESIGN non-goal: "User management beyond simple JWT login"). Tokens live 1 hour.
- **HS256 with one secret**, from `SEATLOCK_AUTH_JWT_SECRET`, with no default outside tests: the app refuses to start without it. One service issues and checks tokens, so an asymmetric key buys nothing yet.
- **`X-User-Id` is removed everywhere**, not kept alongside. Owner checks are added where milestones 2 and 3 deferred them: `GET /holds/{id}` and `GET /payments/{id}` return 404 for another user's resource, as the delivery log already does.
- **Redis rate limiting is a fixed window per user and route,** answered with 429 and `Retry-After`. Redis failures fail open with a WARN: rate limiting protects capacity, not correctness.
- **The seat cache is a 1-second TTL copy of `GET /events/{id}/seats`,** not invalidated on writes. The response can be up to 1 s stale; the hold itself is always checked in Postgres, so staleness can cost a buyer a 409, never a double booking.
- **The worker gets an internal web server** (it has had none since milestone 2) so Prometheus can scrape it. Caddy routes the public domain to the api only. This deliberately reverses milestone 2's "worker has no web server" test.
- **Load is measured locally first.** The README's numbers come from the prod compose stack on the author's machine, with its spec stated. A rerun against the deployed VM replaces them once hosting exists.
- **Deploying is the author's step.** The plan produces the image, the compose file, the runbook and a deploy script; renting the VM, the domain, the GitHub remote and the first deploy need the author's accounts.

## Global Constraints

- Everything in milestones 1-3's Global Constraints still holds (Java 21, Spring Boot 4.1.x, `JdbcClient` not JPA, injected `Clock`, `ProblemDetail` errors, UUID ids, Testcontainers not mocks, `@DirtiesContext(AFTER_CLASS)` on tests that turn background components on, no retrying races, versions from the Boot BOM; find starter names on start.spring.io, do not guess).
- Every request except the public list below needs `Authorization: Bearer <token>`; missing, malformed, expired or wrongly signed → 401 ProblemDetail. Public: `POST /auth/signup`, `POST /auth/login`, `GET /events/**`, `/v3/api-docs/**`, `/swagger-ui/**`, `/swagger-ui.html`, `GET /actuator/health`.
- JWT: HS256, issuer `seatlock`, `sub` = user id (UUID string), `iat`, `exp` = iat + `seatlock.auth.token-ttl` (`PT1H`). Secret property `seatlock.auth.jwt-secret` (env `SEATLOCK_AUTH_JWT_SECRET`), at least 32 bytes, else startup fails with a message naming the property. `@IntegrationTest` sets a fixed 32+ byte test secret.
- Usernames: `^[a-z0-9_]{3,32}$`; passwords: 8-72 characters (BCrypt's limit). Duplicate username → 409. Wrong username or password → 401 with the same detail text for both.
- Rate limits (fixed window, per user id, or per username for login): holds `POST /events/{id}/holds` 10 per 10 s; pay `POST /holds/{id}/pay` 10 per 10 s; login 10 per 60 s per username. Over the limit → 429 ProblemDetail with `Retry-After` (whole seconds until the window ends). Property prefix `seatlock.rate-limit.*`; `seatlock.rate-limit.enabled` (default true).
- Seat cache: key `seatlock:seats:<eventId>`, TTL `seatlock.seat-cache.ttl` (`PT1S`), `seatlock.seat-cache.enabled` (default true).
- Redis is optional at runtime: any Redis error in the rate limiter or cache is logged at WARN and the request proceeds as if Redis were absent.
- Metrics (from Task 3): `management.server.port: 8081`, exposing `health` and `prometheus` only. Custom meters (Micrometer names): counter `seatlock.holds` tag `outcome` = `created|unavailable`; counter `seatlock.payments.settled` tag `status` = `SUCCEEDED|FAILED`; counter `seatlock.webhook.attempts` tag `outcome` = `delivered|failed|dead`; gauges `seatlock.outbox.unpublished` and `seatlock.webhook.pending` (row counts). Built-in `http.server.requests` timers stay on.
- Load test headline: 10,000 distinct buyers, one event of 100 seats. Pass criteria are checked by SQL after the run, never by k6 counters alone: booked seats ≤ 100 and equal to the seats of confirmed holds; no seat in two confirmed holds; one succeeded payment per confirmed hold and none for any other hold; at most one payment per (user, idempotency key); every payment's ledger entries balance (debits = credits).

## Review Focus

1. A token signed with another secret, an `alg: none` token, or an expired one: 401, nothing changed. → Task 1.
2. User A requests user B's hold or payment: 404, as if it did not exist. → Task 1.
3. Redis is down: holds, pay and seat reads still work; rate limiting simply stops. → Task 2.
4. Over the rate limit: 429 with a correct `Retry-After`, and the rejected hold changed nothing. → Task 2.
5. The prod stack started without the JWT secret or database password: it refuses to start rather than run with a default. → Tasks 1 and 4.

### Task 1: Login, JWT and owner checks

**Files:**
- Create: `V4__users.sql`, `auth/*`, test `TestTokens`, `auth/AuthApiTest`, `auth/SecurityTest`
- Modify: `pom.xml`, `application.yaml`, every controller and test using `X-User-Id`, `ApiExceptionHandler`, `hold/HoldService` + `HoldController` (owner check), `payment/PaymentService` + `PaymentController` (owner check), `IntegrationTest` (test secret property)

**Interfaces:**
- Produces table `users(id uuid pk, username text not null unique, password_hash text not null, created_at timestamptz not null)`.
- Produces HTTP: `POST /auth/signup {"username","password"}` → 201 `{"id","username"}`; `POST /auth/login {"username","password"}` → 200 `{"accessToken","tokenType":"Bearer","expiresIn":3600}`.
- Produces Java: `TokenService.issue(UUID userId)` → token string. Controllers get the caller's `UUID` from the authenticated JWT's `sub` through one shared helper (`CurrentUser`), not repeated parsing. Test helper `TestTokens.bearer(UUID userId)` returns the header value, minted with the app's `TokenService` bean.
- 401 and 403 from Spring Security are ProblemDetail JSON (custom `AuthenticationEntryPoint` / `AccessDeniedHandler`), with `WWW-Authenticate: Bearer`.
- Stateless sessions, CSRF off (bearer tokens only), no form login, no HTTP basic.

  - Startup without a usable secret: an `ApplicationContextRunner` (or `SpringApplicationBuilder`) with `seatlock.auth.jwt-secret` blank or 16 bytes fails, and the failure message names the property.

### Task 2: Redis rate limiting and seat cache

**Files:**
- Create: `ratelimit/*`, `event/SeatCache.java`, tests `ratelimit/RateLimitTest`, `event/SeatCacheTest`
- Modify: `pom.xml`, `application.yaml`, `TestcontainersConfiguration` (static `redis:7` container, same pattern as Postgres/Kafka), `EventService.listSeats`, hold and pay controllers (or an interceptor), `AuthController` (login limit), `ApiExceptionHandler`, `IntegrationTest`, `compose.yaml` (+ redis service on 6379)

**Interfaces:**
- Produces: `RateLimiter.check(String bucket, int limit, Duration window)` → throws `RateLimitExceededException(long retryAfterSeconds)` (→ 429 + `Retry-After`). Implementation: `INCR seatlock:rl:<bucket>:<window index>` with `EXPIRE` on the first increment, where window index = epoch seconds / window seconds from the injected `Clock`. Bucket names: `hold:<userId>`, `pay:<userId>`, `login:<username>`.
- Produces: `SeatCache.get(UUID eventId, Supplier<List<Seat>> load)` → cached list, or the `load` result (which it then caches).
- `@IntegrationTest` adds `seatlock.rate-limit.enabled=false` and `seatlock.seat-cache.enabled=false` to its defaults (milestone 1's 1,000-concurrent-hold test must not be rate limited or cached); the new tests turn them on.

- [ ] **Step 1: Write the failing tests**

  - Fail-open (nested class with `spring.data.redis.port` pointed at a closed port, rate limit and cache on): holds, pay and `GET /events/{id}/seats` all succeed.
  - `SeatCacheTest` (cache on): change a seat's status directly in SQL between two reads → the second read still shows the old state (served from Redis); after the TTL passes (Awaitility, ≤ 3 s) the change is visible.
  - The milestone 1 concurrency test still passes unchanged.

### Task 5: Load test with SQL-checked results

**Files:**
- Create: `load/hold-rush.js`, `load/verify.sql`, `load/README.md`, `load/results/2026-11-local.md`

**Interfaces:**
- `hold-rush.js` (k6): `setup()` signs up an organizer, creates one event with 100 seats at 2500 MYR, and returns the seat ids. Buyer tokens are minted inside k6 with `k6/crypto` HMAC-SHA256 from `SEATLOCK_AUTH_JWT_SECRET` (env), one random UUID `sub` per iteration, so 10,000 buyers need no signups and each stays far under the per-user rate limits. Scenario `shared-iterations`, 10,000 iterations, VUs from env (default 500). Each iteration: hold one random seat; on 201 pay with `Idempotency-Key: <uuid>`, then send the same pay again with the same key and check the same payment id comes back; on 409 stop. Custom counters: `holds_created`, `holds_conflicted`, `pays_ok`, `pay_replays_matched`. Expected statuses 200, 201, 202 and 409 (`http.setResponseCallback`), so `http_req_failed` counts only real failures; thresholds `http_req_failed rate == 0` and `checks rate == 1`.
- `verify.sql`: one query per pass criterion in Global Constraints, each returning `(check_name, passed boolean, detail)`, run with `psql -v event_id=...`.
- `load/README.md`: how to run against the local prod stack, how to run `verify.sql`, how to read the results.

- [ ] **Step 1: Run** the scenario against the local prod stack from Task 4 at 500 VUs, wait for settlement to drain (no PENDING payments), run `verify.sql`; every check passes. Save the k6 summary (requests/s, p95/p99 for hold and pay, the counters) and the verify output to `load/results/2026-11-local.md`, with the machine (CPU, RAM, OS) and the stack's settings.
- [ ] **Step 2: Mutation check** (proves the SQL can fail): on a scratch copy of the database, insert a second confirmed hold for a booked seat; `verify.sql` reports that check as failed. Record it in the results file; do not commit the scratch change.
