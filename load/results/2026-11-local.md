## verify.sql (after settlement drained: 0 PENDING payments; fresh stack, fresh data)

| check | passed | detail |
|---|---|---|
| guard: event exists, 100 seats, >= 1 confirmed hold | t | events=1, seats=100, confirmed holds=100 |
| booked seats <= 100 and = seats of confirmed holds | t | booked=100, seats in confirmed holds=100, booked seats in confirmed holds=100 |
| every confirmed hold owns a booked seat | t | confirmed holds without a booked seat=0 |
| no seat in two confirmed holds [guaranteed by seats.hold_id] | t | 0 |
| one succeeded payment per confirmed hold, none for others | t | violating holds=0 |
| at most one payment per (user, idempotency key) [guaranteed by unique(user_id, idempotency_key)] | t | duplicated keys=0 |
| ledger balanced per payment | t | unbalanced payments=0 |
| no PENDING payments left | t | pending=0 |

100 holds, all CONFIRMED. Run with a random UUID as `event_id`, the guard fails (`events=0, seats=0, confirmed holds=0`) while the other rows pass vacuously, so a wrong id cannot go unnoticed. Raw: [`task-5-verify.txt`](raw/task-5-verify.txt).

Two checks cannot fail on real data because the schema guarantees them: "no seat in two confirmed holds" (a seat has one `seats.hold_id` column; no hold-seat table) and "at most one payment per (user, idempotency key)" (`unique (user_id, idempotency_key)`, constraint `payments_user_id_idempotency_key_key`). They are kept as tripwires and labelled so in the SQL. The schema stores no seat count on a hold, so the per-hold check is ">= 1 booked seat"; the total is the booked = seats-of-confirmed-holds check.

## Mutation checks (a fresh scratch copy of the database per mutation, all dropped afterwards)

| mutation | check that failed | others |
|---|---|---|
| A. double-sell: second CONFIRMED hold for the event with a SUCCEEDED payment and balanced ledger entries (it owns no seat, because `seats.hold_id` keeps only the first hold) | every confirmed hold owns a booked seat (1 hold without a seat) | all other rows pass (guard shows 101 confirmed holds) |
| B. +1 cent on one ledger credit | ledger balanced per payment (1) | all others pass |
| C. CONFIRMED hold with no payment and no seat | every confirmed hold owns a booked seat; one succeeded payment per confirmed hold | others pass |

A second SUCCEEDED payment for an already-paid hold is refused by `payments_hold_id_key` (unique on `hold_id`), so it cannot be inserted. A second confirmed hold cannot own a booked seat (single `seats.hold_id`). The mutations exercised: the guard (random UUID), the new per-hold check (A, C), the payment-per-hold check (C), the ledger check (B). Not exercised by any mutation, because the schema makes them impossible to break: seat-in-two-holds and duplicate (user, key). Raw: [`task-5-mutation.txt`](raw/task-5-mutation.txt).

Note: before this fix, mutation A (all of its payment and ledger rows consistent) passed all six checks; that was the gap.

The `p(95)<1000` hold threshold was removed from the script because it was my own addition, not in the task, and latency on a laptop running k6 and the whole stack is not a correctness criterion: the pass criteria are the SQL checks. The three `p(99)<60000` thresholds that remain exist only so k6 prints per-request-type percentiles.

The script now counts any unexpected status in `unexpected_status` (tagged by step and status) and logs the first three per VU, so a future failure says what it was.
